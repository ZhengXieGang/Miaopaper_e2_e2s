**真机首刷已执行并通过恢复验证**（2026-11-22 19:06、20:00 两次写入 r7，19:07/20:02 两次 ② 切回原厂 1.3.739；2026-11-23 01:51 写入 r8 并核对到 `hello-paperang-r8`）。r9 起修正了固件结束后应答被原厂事件队列吞掉时的处理：不再把 `(2,2)` 静默当作失败，而是继续发 `(1,19)` 触发升级。当时的 APK 为 r23，镜像为 r20。r10/r11 的诊断确认 `bus/dev/draw/wr=4000` 全部正常，问题在面板通信与 BUSY 语义：原厂 discern 在复位后 **GPIO47=1 才读 ID**，即**高电平=就绪、低电平=忙**；我们之前把 `busy_wait` 写成“高电平忙”，结果激活刷新后 BUSY 变低时等待立刻退出，紧接着发深睡指令，**把正在进行的刷新打断**——这就是屏幕一直不变的原因。r12 修正了 BUSY 极性、读事务和激活后延时，诊断变为 `rd=0 draw=0 wr=4000 ms=2006 id=3fffffffff`：代码全通，但 `ms=2006` 说明 BUSY 全程为高、面板从未进入忙状态，`id=3f ff ff ff ff` 是 MOSI 空闲高电平（面板没回数据）。继续反汇编发现原厂刷新用的是**双 RAM bank**：`0x13` 写旧数据、`0x26` 写新图像，然后 `0x22 C7 + 0x20`；r12 之前把图像写进了 `0x13`（旧 bank），新 bank 从未写过。r13 改为 `0x13` 全白 + `0x26` 本帧图像，诊断变为 `wr=8000 ms=2010 id=3fffffffff`：两个 bank 都发了，但 BUSY 仍全程为高、ID 仍是空闲高电平，说明面板没有通过 SPI 外设收到任何东西。r14 改用**纯 GPIO 位翻转**绕开 SPI 外设，诊断变为 `id=ffffffffff pins=0000`：ID 仍是空闲高电平；`pins=0000` 是误读——输出脚用 `GPIO_MODE_OUTPUT` 时输入通路关闭，`gpio_get_level` 恒为 0。r15 把输出脚改成 `GPIO_MODE_INPUT_OUTPUT`、加读温度寄存器 0x40、暂不深睡并等 20 秒。r15 诊断 `temp=ffff id=ffffffffff pins=1000`：GPIO 确实被驱动（CS=1、DC=0、SCLK=0），但面板对 0x70 和 0x40 都不应答。结合“恢复原厂后屏幕也一直是固件更新中”，当前怀疑面板被之前的 `0x07 A5` 深睡锁住，需要原厂按键唤醒路径或一次真正断电才能退出——r16 补上 `0x17 0xA5` 后诊断仍是 `temp=ffff id=ffffffffff busy=1`，没有变化。r17 改做一次真正的**掉电复位**：39/40/48 全部拉低 200ms，再按 48→40→39 顺序上电并等 500ms（若面板电源/复位由其中任一脚门控，可清掉深睡锁存）；同时在初始化**之后**再读一次 ID（`id2=`）。实机确认了一个关键现象：**r17 时屏幕发生了全局刷新（闪了一下）但内容没变**——说明面板确实收到并执行了我们的刷新/激活命令，问题只在**图像数据没有写进可见 RAM**。r18 先补了 `gpio_hold_dis`（原厂轻睡/重启可能 hold 住 EPD 引脚）。r19 把图像同时写进 `0x13`/`0x26` 两个 bank 后，实机**完全没有变化**——r17 那次全刷更可能是原厂固件的周期性全刷，而不是我们触发的。这说明命令可能根本没到面板。最后一个未复现的软件差异是 SPI 外设本身：原厂用 `spi_bus_initialize(2, …)` 即 **SPI3_HOST**，唯一设备配置为 `3WIRE|HALFDUPLEX`，DC 由 pre_cb 按 `transaction.user` 驱动。r20 完全照抄：SPI3 + 3 线半双工 + pre_cb + 手动 CS=40 + 10MHz，并保留掉电复位、`gpio_hold_dis`、双 bank 图像。r20 实机仍是“固件更新中”不动。随后把原厂 **0x42029c68（EPD 状态机）**整段重新对齐反汇编，确认了两处 r20 仍然漏掉的差异：① 原厂初始化在四张 55B LUT 之后并不是直接 `0x41 07`，而是 `wait BUSY -> 写 0x13 帧 -> wait BUSY -> 0x17 A5（auto sequence）-> wait BUSY -> 0x41 07`（0x4202a5b0–0x4202a5bf），r20 少了 `0x17 A5` 这一步；② 原厂刷新路径在 `0x12` 之后、以及 `0x22/0x20` 之前等的是 **BUSY 回到低电平**（0x420298a0：`while(47==1) delay`，25 秒超时），而 r20 的 `busy_wait` 等的是高电平，于是 `0x12` 后立刻返回、后续配置和图像都发在复位过程中被丢弃。r21 补上 `0x17 A5` 初始化尾部（先写一帧全白到 `0x13`），并把所有关键等待改成**反应式**：先记住 BUSY 当前电平，等它翻转（证明面板确实响应），再等它回到原电平（操作完成），不依赖高/低极性；每次等待的 `起始电平>结束电平/耗时` 都放进 `(1,241)` 的 `ev=` 字段，即使屏幕仍不动，也能从轨迹判断面板到底有没有反应。随后对照本地 `firmware/e2s_re`（1.3.739 一比一还原）发现它有三处不可直接照抄的结论：引脚写成 `CS=39/DC=46/PWR=40`（实测汇编是 **CS=40、DC=39**，GPIO46 属音频功放）、模式表 0 标成“全刷”（实际 0x4202a5f4 日志是 `"sm idle"`，1 号 0x42029e9c 才是 `"sm cfg"` 绘制路径）、把 SPI 写成 `SPI2_HOST`（原厂是 `spi_bus_initialize(2,…)` 即 SPI3_HOST）。但它的模式表地址和 15 张 LUT 是对的，并据此确认原厂按 **GPIO47 分面板族**：复位后 `47==0` → **BOE**（type 1），走 SSD1680 风格 `0x12/0x32 153B/0x26/0x22 C7/0x20`；`47==1` → 读 `0x70` ID，`id[2]==5` → **OED**（type 3），走 UC8151 风格 `0x00 FF89/01/03/06/30/60/82/E3/61/65/50 + 55B LUT + 0x13 帧 + 0x17 A5`；`47==1` 且 ID 不是 5 → 原厂记 `"epd type discern err high"`，type 0（GD）**直接不刷新**。r22 因此不再无条件混发两套命令：开机按原厂 discern 规则读 `p47` 分族，BOE 只发 SSD1680 那套、OED 只发 UC8151 那套，并把 `fam=`/`p47=` 写进诊断。r22 实机**屏幕从“固件更新中”变成全黑**——面板终于执行了刷新，说明 SPI/引脚/分族全部打通，只剩图像数据的极性/可见 RAM bank。但 r22 的 `(1,241)` 应答被 `respond()` 的 `frame[128]` 静默丢弃（内容超过 111 B），所以没读到轨迹。r23 修掉应答缓冲（`RESP_MAX=512`，输入累加器仍 128），把测试图改成 **8px 黑边框 + Hello Paperang**（一眼判断方向/极性和窗口），并在两个族里补写可能可见的 bank：BOE 写 `0x13/0x24/0x26`，OED 写 `0x10/0x13`，避免未初始化的旧 bank 把全刷驱动成全黑。r23 实机 **`(1,241)` 完整读回**：`fam=1 p47=0`（BOE 族）、`draw=0 wr=12000 ms=28013`，BUSY 轨迹 `b0:1>0/5003,b1:0>0/1499,b2:0>0/1499,b3:1>1/19999`——命令全部到达、BUSY 有翻转，但激活后 BUSY 一直为高 20 秒，屏幕是灰边框+全黑内部。对照原厂 DROM 逐字节核对后找到根因：**`epd_lut_stock.h` 里的 LUT 数据整体错位**。原厂 `0x3c17b6a9` 的 55B 是 `00 14 14 01 01 00 01 00` + 47 个 0，我们的数组却是 23 个 0 + `0x3c17b6e0` 的 153B 表内容；`s_lut153` 又从 `0x3c17b6e0` 偏移 8 字节开始并串进了 `"power_manager"` 字符串。也就是说 r7–r23 一直在发**错位的垃圾波形**，面板能执行 0x12/0x20 但刷新波形不对，所以全黑/卡 20 秒。r24 从原厂 `drom.bin` 的 `0x3c17b6a9/0x3c17b5c9/0x3c17b639/0x3c17b601/0x3c17b6e0` 重新生成全部 5 张表，并去掉 BOE 路径里对 `0x24` 的 4000B 写入——`0x24` 在原厂初始化里是 55B LUT 寄存器（BB 波形），写图像会覆盖波形表；BOE 刷新恢复为原厂的 `0x13`/`0x26` 两个数据 bank。r24 实机 `(1,241)` 读回 `wr=8000 ms=28012 ev=...b3:1>0/19999`：刷新完整跑完，但屏幕仍是面板 RAM 里的旧图（“固件更新中”）。重新对齐原厂 BOE 分支（0x4202a07d / 0x4202a137）后确认：**写帧命令是 `0x24`（B/W RAM）和 `0x26`，`0x13` 只属于 OED/UC8151 分支**；r24 写的 `0x13` 不是 BOE 的可见 bank（SUMMARY 里的 `0x13/0x26` 是把两条分支看混了）。另外 `0x5000006c` 是面板类型全局：GPIO47=0 → 1（BOE），47=1 且 ID[2]=5 → 3（OED），与实机 `fam=1 p47=0` 一致。r25 只改一处：BOE 写帧改为 `0x24` + `0x26`（LUT 不变）。r25 实机**图像终于出现**（白底、黑框、黑字），但文字镜像且画面上下倒置，说明面板 X 扫描方向与假设相反；r26 只改 `build_fb`：把图像 y 轴取反后再装入 RAM（`u = 121 - y`），其余不动。r26 实机方向正确，但 “Paperang” 显示成 “Paberang”：字体表里 `p` 的字形与 `b` 完全相同（96 个字形里唯一的重复项，缺少降部），r27 只改这一个字形（`p` 的碗形保留、补上 `0x60 0x60 0x60` 降部）。App 现为 Compose（MD3）通用版：扫描并选择任意 E2S，固件可选内置示例或本地 `.bin`；刷入会自动预检、必要时先切回原厂，再写入并验证启动。

## 操作

- **刷入固件**：扫描并选择 E2 / E2S 后点击，二次确认。流程自动核对 E2 / E2S 型号和当前固件；已是原厂则直接写入，否则先切回原厂槽并等待重启；随后核对电量与设备参数，再通过原厂 OTA 服务把所选镜像写入非运行槽、切换启动并验证新版本。
- **恢复原厂**：二次确认。只切回原厂槽并验证启动，不上传固件。
- **固件来源**：通过系统文件选择器选任意本地 `.bin`（不随 APK 打包任何示例固件）。本地会校验 ESP app magic `0xE9`、大小 ≤ `0x1F0000` 和 SHA-256，并解析 `esp_app_desc_t` 版本摘要；非官方镜像刷错只能 UART 恢复。

刷入前会校验本地镜像 SHA-256；任一步无明确应答就停止，不自动重试。设备版本、电量和设备参数用于识别与写入保护，不是密码学认证。

**结束/触发策略（r9 起）**：原厂 `(2,2)` 处理器先 `fclose` 缓存文件、再整文件读回，最后才把一个 24 字节事件用**零超时** `xQueueSend` 投给 data_sync 队列；队列忙时事件被静默丢弃，但文件已经写完并关闭。因此 r9 只等 20 秒 `(2,2)`，无应答也继续发 `(1,19)`（最多 3 次，每次 8 秒）。`(1,19)` 自身也走同一队列，所以也可能被吞；镜像仍由 `esp_ota_end` 校验魔数与 SHA-256，重复触发或半截文件都不会改启动槽。r9 实测还发现：A5 没有请求序号，`(2,2)` 超时会把上传用的 Exchange 永久置为失败（这是刻意的防串包设计），所以 r11 改为**关闭上传会话、重新连接并握手后再发 `(1,19)`**，最多 3 次。

切换启动会改 `otadata`，**不是只读操作**。恢复只有在重连后读到 E2S 型号和形如 `x.y.z` 的原厂版本时才算成功；结果未知时不会自动重试。

## BIN 里能确定什么

原厂 `downloads/paperang_e2s-v1_3_739_e5938.bin` 是 **App-only 镜像**，本身不含分区表，所以不能从它直接读出各分区的偏移和大小。但它给出了这些可核对事实：

- 原厂 OTA 代码调用标准的 `esp_ota_get_next_update_partition`、`esp_ota_begin/write/end/set_boot_partition`，即标准 otadata + 两个 OTA 槽路径。
- 镜像中没有 `esp_ota_mark_app_valid_cancel_rollback` 调用；按 ESP-IDF 语义，回滚试启动基本未启用，OTA 提交后的 otadata 状态为 `UNDEFINED`。
- 镜像长度不是 4096 的倍数，未见 Secure Boot v2 签名块；Secure Boot 很可能未启用。应用安全版本为 0。
- 原厂镜像 2,026,352 B，距 `0x1F0000`（2,031,616 B）只差 5,264 B；`0x1F0000` 是很可能的单槽大小。
- 原厂 App 头的 flash size 字段写 8 MB，但设备信息 JSON 自报“内部 4MB + 外部 128MB”。两者不一致，真实内部容量没有读回；r7 仍按 8 MB 头构建以匹配原厂头，但绝不假设多出的地址可用。

由于原厂 OTA 路径会自己计算目标槽，刷入不需要知道分区表偏移。刷入只写非运行 OTA 槽，原厂槽不会被覆盖；但**这仍不能证明测试固件一定能启动**。真实物理 flash、分区表、Flash Encryption 状态、引导回退行为都无法从 App 镜像确认；如果测试固件在 BLE 起来前崩溃，就只能用 UART/esptool 恢复。

## 已核对的协议差异

- FF00 是服务，FF01 是 A5 应答通知，FF02 是写入，FF03 是就绪通知。两路 CCCD 串行写；FF03 `{1,3}` 是 E2S 类型，`{2,分段大小 LE16}` 已扣 ATT 开销，不重复减 3。原厂有时在订阅生效前就发一次 FF03；检查版最多等 3 秒，收不到就用协商 MTU−3 继续，不阻塞。
- A5 帧为 `A5 01 [payloadLen LE16] [payload] [CRC32 LE32] 5A`。校验使用原厂初始值 `896963873`（`0x35769521`）的 CRC-32，**不是** zlib 默认的 `0xFFFFFFFF`；用错初始值时原厂固件会按 CRC 错误静默丢弃。`(1,23)` 请求的 TLV 1 是 16 个 ASCII 十六进制字符；原厂回显 challenge，r7 同样回显，不实现原厂鉴权。查询应答为 `status + len16 + data`；原厂 `(1,8)` 的型号在第二个 TLV，r7 返回裸 `E2S`，检查版区分这两种结构。
- 原厂文件块 `(2,3)` 的 content 是块号 LE16、块长 LE16、原始数据，不是三个 TLV。r7 本身不接收 `(2,x)`；首刷时是**原厂固件**接收这些块，r7 只负责之后切回原厂槽。
- 本地原厂 `1.3.739` 镜像是 2,026,352 B。整文件 SHA-256 为 `162e7c552254726f6e231888bd1d0ba09007ced7cc1b83f2276641b225db740e`，镜像内附 SHA-256 为 `dd9887c68b741ae92b34ee1a4b6f70e4a1c1a40ce521a9cf8a8b7c599deede63`。前者用于本地文件比对，后者由 ESP-IDF 在槽内重算并核对；不是本轮重新向云端校验的结果。

- EPD 引脚和时序已按原厂 `epd_hal_gpio_init` / SPI 辅助函数反汇编确认：**CS=40、DC=39、RST=48、BUSY=47、MOSI=41、SCLK=42**。没有独立 PWR 脚，也没有 GPIO46：`epd_hal_gpio_init` 只把 39/40/48 配成输出并置高、47 配成输入上拉；每个写事务由代码拉低/拉高 40，传输前置回调按 `transaction.user`（0=命令、1=数据）驱动 39，读事务则手工拉低/拉高 39。r8 按原厂全刷路径重写：初始化写 `0x00 FF89 / 0x01 03 00 3F 3F 03 / 0x03 / 0x06 27 27 2F / 0x30 09 / 0x60 22 / 0x82 00 / 0xE3 / 0x41 / 0x61 80 00 FA / 0x65 / 0x50 B7×2`，再写 `0x20/0x24/0x22/0x23` 四张 55 字节全刷波形表（原厂 DROM 0x3c17b6a9/0x3c17b5c9/0x3c17b639/0x3c17b601），然后按原厂顺序 `wait BUSY -> 0x13 全白帧 -> wait BUSY -> 0x17 A5 -> wait BUSY -> 0x41 07`；每帧重发 `0x12 / 0x01 FA0000 / 0x11 03 / 0x21 0080 / 0x18 80 / 0x3C 05 / 0x3F 22 / 0x03 17 / 0x04 41A832 / 0x2C 58` + 153B `0x32` 波形，再设窗口、`0x13`/`0x26` 各发完整 4000B、`0x22 C7` + `0x20`。r7 既缺 0x20-0x24 寄存器、153B LUT 内容也不对，是空白的直接原因；r21 又补上了 0x17 A5 与正确的 BUSY 等待方向；r22 按 `p47` 分族，只发对应面板族的那一套，不再混发。
